03

Податоците се поделени

The data is split up

Секој сервис има свои табели. Погледни што има, и што нема, сервисот за огласи.

Each service has its own tables. Look at what the listings service has, and what it doesn't.

Кога ќе отвориш оглас, треба да се види името и телефонот на продавачот. Сервисот за огласи го има само продавач_id — бројката. Името е во другата табела, во другиот сервис.

When you open a listing, the seller's name and phone have to show. The listings service only has seller_id — a number. The name sits in the other table, in the other service.

Може да му го побара од сервисот за корисници секој пат. Но тогаш, ако тој сервис не работи, не се отвораат ни огласите. Затоа го правам обратно: при регистрација, сервисот за корисници праќа порака, а сервисот за огласи си го запишува тоа што му треба.

It could ask the users service every single time. But then, if that service is down, listings stop opening too. So I do it the other way round: on registration the users service sends a message, and the listings service writes down what it needs.

04

Што ако пораката не се прати

What if the message doesn't get sent

Марко си го менува телефонот. Две работи треба да се случат, една по друга.

Marko changes his phone number. Two things have to happen, one after the other.

  1. Сервисот за корисници го запишува новиот телефон во својата табела. The users service writes the new phone number into its table. готово ✓ done ✓
  2. Истиот сервис праќа порака, за да го дознае и сервисот за огласи. The same service sends a message, so the listings service finds out too. тука може да падне ✕ this is where it can fail ✕

Чекор 1 веќе е направен и не се враќа назад. Значи телефонот е нов во еден сервис, а стар во другиот — и ништо никаде не пишува што тоа се случило.

Step 1 already happened and doesn't get undone. So the phone is new in one service and old in the other — and nothing anywhere records that this happened.

Решението е да не ги разделувам. Пораката се запишува во истата база, во истиот момент како и телефонот — како обичен ред во табела со незапратени пораки. Запишувањето е едно: или двете, или ниедно.

The fix is to not separate them. The message is written into the same database, at the same moment as the phone number — as an ordinary row in a table of unsent messages. It's a single write: either both, or neither.

едно запишување во базата
one write to the database
нов телефонnew phone numberво табелата „корисници“in the "users" table
порака за праќањеmessage to sendво табелата „незапратени“in the "unsent" table

Потоа мала програма ја чита таа табела и ги праќа пораките. Ако Kafka не работи, пораката си стои и чека; кога ќе се врати, се праќа. Ништо не се губи — само се задржува.

Then a small program reads that table and sends the messages. If Kafka is down the message just sits and waits; when it comes back, it goes out. Nothing is lost — it's only delayed.

а ако истата порака се прати два пати, сервисот за огласи препознава што веќе ја примил

and if the same message goes out twice, the listings service recognises it already got it

05

Како ќе го измерам

How I'll measure it

Не „еве, работи“ — три проверки со број на крајот.

Not "look, it works" — three checks with a number at the end.

проверка 1check 1 Гасам Kafka среде операција Kill Kafka mid-operation → 0 изгубени настани → 0 events lost
проверка 2check 2 Праќам ист настан два пати Deliver the same event twice → 1 известување → 1 notification
проверка 3check 3 Оптоварување врз двете верзии Load against both versions → монолит vs. сервиси → monolith vs. services

Ако те притиснат

If they press

Зошто повторно го пишуваш истото?

Why rewrite the same thing?

Затоа што функционалноста ја знам — па можам да ја споредувам архитектурата, а не да учам нов домен.

Because I already know the functionality — so I can compare architectures instead of learning a new domain.

Зошто Java, а не .NET?

Why Java and not .NET?

Spring Boot со Spring Cloud има готов gateway и Kafka интеграција, и е тоа што ќе го работам понатаму.

Spring Boot with Spring Cloud gives me the gateway and Kafka integration out of the box, and it's what I'll be working in.

Монолит би бил доволен?

Wouldn't a monolith do?

За функционалноста — да, и веќе го имам. Но тогаш ја нема работата: дистрибуираниот дел е темата.

For the functionality, yes — I already have one. But then there's no work left: the distributed part is the subject.

Каде е придонесот?

Where's the contribution?

Споредба на истата апликација во две архитектури, со измерено однесување кога нешто паѓа.

A comparison of the same application in two architectures, with measured behaviour under failure.

Не е ли обемот преголем?

Isn't the scope too large?

Затоа и кажувам што не влегува. Ништо ново во функционалност — само преработка и мерење.

That's why I say what's out. No new functionality — only the rework and the measurements.

Зошто Kafka, а не REST повици?

Why Kafka and not REST calls?

Со директен повик, ако другиот сервис е паднат паѓа и моето барање. Со настани, барањето поминува.

With a direct call, if the other service is down my request goes down with it. With events, the request completes.
